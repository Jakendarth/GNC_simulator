# Maintaining the technical wiki

Use this guide to preview documentation, update the correct source files and prepare changes for review. Run the commands from the repository root. Website tooling uses a separate Python environment from the simulator.

## Documentation ownership

| Location | Responsibility |
| --- | --- |
| `openwiki/` | Generated technical reference, indexes and evidence managed by OpenWiki |
| `docs/` | Topic explanations, pipeline examples, publications, demonstrations and website assets |
| `scripts/build_docs.py` | Build-time integration of OpenWiki, function signatures, logo and selected videos |
| `docs/conf.py` and the homepage toctrees | Navigation, theme, extensions and link validation |
| `requirements-docs.txt` | Pinned documentation tools, separate from simulator dependencies |
| `site/` | Ignored build output; uploaded as the GitHub Pages artifact |

The build script stages maintained Markdown, public OpenWiki pages and media in a temporary directory, then runs Sphinx with the Read the Docs theme. It adapts OpenWiki directory links and legacy inline-math delimiters only in that temporary copy. Hidden evidence records (Claims), manifests and run-state files remain outside the public site.

The function catalog at `reference/functions.md` is generated by parsing Python's abstract syntax tree (AST). This reads definitions without importing application modules or running the graphical interface or solvers. Signatures and source links update automatically. Explanations and examples under `docs/topics/` and `docs/pipelines.md` still need review when behavior changes. Earlier definitions replaced by a later definition of the same name are labeled as shadowed.

The header, favicon and homepage reuse `assets/GNC_sim_logo.png`. The script exposes four selected MP4 files from `output/` as site assets without duplicating their source binaries. Video posters under `docs/assets/video-posters/` are extracted middle frames.

Organisation and project logos live under `docs/assets/branding/`, with their original sources recorded in `sources.json`. SAFE-NET reuses `assets/safenet.png`. Keep these identifiers unmodified and legible on their white logo panels. The build also stages the repository's `LICENSE` and `NOTICE` for download and includes the additional copyright disclaimer directly from LICENSE on the Organisations page, so its wording stays synchronized.

For a recording change, update the build script's media list and `docs/demonstrations.md`. Supply a descriptive caption, a download link, `preload="none"` and a matching poster. The HTML media URLs rely on directory-style page URLs; check them if changing that setting.

For a publication change, edit metadata, DOI links, BibTeX and proceedings status in `docs/publications.md`, then update the topic links. Verify final details before replacing author-supplied forthcoming metadata. Record experiment configurations before identifying a video as a particular paper's experiment.

When adding or moving a page, update the `{toctree}` blocks in `docs/index.md` and incoming links. Theme, parser and extension settings live in `docs/conf.py`. The strict build treats Sphinx warnings as errors and checks the rendered site for missing links, anchors, images and videos.

## Build and preview locally

Install Python 3.13 to match continuous integration (CI), then create and activate a documentation environment:

```sh
python3.13 -m venv .venv-docs
source .venv-docs/bin/activate
python -m pip install -r requirements-docs.txt
python scripts/build_docs.py
python -m http.server 8000 --directory site
```

The build writes HTML under ignored `site/`. Open http://127.0.0.1:8000/ after starting the HTTP server. Rebuild after editing a page, then refresh the browser; this server does not rebuild automatically. Check the sidebar, search, light/dark themes, code-copy controls, diagrams, equations, the logo and all four video players. Press Ctrl+C to stop the server.

The script runs Sphinx with `-b dirhtml -W --keep-going -n`, then validates local HTML links, fragments and media references, including raw video URLs. Directory-style URLs preserve the existing page paths. The build does not run a simulation, check remote websites or prove browser-side playback and rendering.

Maintain pages as MyST Markdown. Use standard Markdown tables, `{admonition}` colon fences for notes, Mermaid code fences for diagrams, and dollar-delimited mathematics. Existing inline \( ... \) expressions are adapted during staging. Sphinx uses MathJax for equations and sphinxcontrib-mermaid for diagrams, with pinned browser-runtime versions loaded from a content delivery network (CDN). Keep figures under `docs/` and use relative links. Generated OpenWiki content remains owned by OpenWiki.

## Regenerate the technical reference

1. Confirm that the application source and authoritative documentation describe the intended behavior. Make source changes separately if needed.
2. Ask an OpenWiki-enabled coding agent to update this repository's OpenWiki from the current source and tests. Alternatively, use the existing OpenWiki CLI integration described below.
3. Review the generated changes and evidence. Preserve OpenWiki-managed metadata; do not hand-edit Claims or run-state files.
4. Update maintained introductions and the homepage toctrees if the topic structure changed. Adjust `docs/conf.py` when parser or theme settings need to change.
5. Run `python scripts/build_docs.py`, preview the result and submit the changes for review.

The separate `.github/workflows/openwiki-update.yml` supports a daily schedule and manual dispatch. It uses `openwiki@0.9.0`, the configured provider/model and repository secrets to open an update pull request. Check the workflow configuration and its run result before relying on an automated refresh.

The Sphinx website workflow builds repository content without a model-provider key. Regeneration and publication are separate operations; an editorial rewrite of maintained pages does not require an OpenWiki refresh.

With OpenWiki installed and its provider credentials configured, the repository workflow's update command can also be run locally:

```sh
openwiki code --update --print
```

Check the existing workflow's provider, model and tracing configuration before running this command. These instructions do not configure credentials or establish that a remote regeneration succeeded.

## Deployment and review

Use a pull request to review documentation changes. `.github/workflows/docs.yml` runs the strict build for relevant pull requests and deploys only from `main`. A manual dispatch from another branch builds without deploying.

Relevant pushes to `main` include documentation, configuration, Python source, the logo and MP4 files. Source changes refresh catalog signatures automatically, while conceptual OpenWiki pages still need a reviewed regeneration when behavior changes.

The workflow uses GitHub's Pages configuration, artifact-upload and deployment actions. Builds have read-only repository access. Only deployment receives `pages: write` and `id-token: write`, using the `github-pages` environment. Production runs share a concurrency group so an active deployment is not cancelled by another run.

Before the first deployment, a repository maintainer must:

1. In **Settings → Pages → Build and deployment**, set **Source** to **GitHub Actions**.
2. Allow GitHub Actions and the actions used by `docs.yml` under **Settings → Actions → General**, if repository or organization policy currently blocks them.
3. Ensure the **github-pages** environment permits deployment from `main`. Add required reviewers there if each publication should require approval, where supported by the repository's plan.
4. Review and merge the documentation branch. A qualifying push to `main`, or a manual dispatch on `main`, will deploy to [the manual's configured URL](https://jakendarth.github.io/GNC_simulator/).

No `gh-pages` branch or personal access token is needed for the website workflow. A local build does not publish anything.

References: [GitHub Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [Read the Docs theme](https://github.com/readthedocs/sphinx_rtd_theme), [MyST Markdown](https://myst-parser.readthedocs.io/en/latest/), and [Sphinx Mermaid](https://sphinxcontrib-mermaid-demo.readthedocs.io/en/latest/).
